## 1. Project Overview

### 1.1 Purpose

This project will develop a web-based educational tool that demonstrates how C source code is translated into RISC-V machine instructions.

The application will contain three linked panes:

1. **C Source Code:** Displays the original C program.
2. **RISC-V Assembly:** Displays the assembly generated by the compiler.
3. **Machine Code:** Displays the hexadecimal and binary encoding of each supported instruction.

When a user selects or hovers over a line of C code, the application will highlight the corresponding assembly instructions and machine-code entries whenever a reliable source mapping is available.

The machine-code pane will also display a color-coded breakdown of each instruction's encoding fields, such as the opcode, destination register, source registers, function fields, and immediate value when applicable.

The project is intended to help students understand the relationship between high-level programming, assembly instructions, and the binary representations executed by a processor.

### 1.2 Project Goals

The application will:

- Compile supported C programs into RISC-V assembly using an existing cross-compiler.
- Display the generated assembly and its corresponding machine-code encodings.
- Decode supported instructions using a custom RV32I instruction decoder.
- Connect C source lines to generated assembly instructions and machine-code entries.
- Demonstrate how compiler optimization changes generated code.
- Provide example programs and exercises that students can use independently.
- Include documentation and automated tests so the project can be maintained and extended.

### 1.3 Scope

The project will focus on **32-bit RISC-V using the base integer instruction set, RV32I**.

The compiler will handle C parsing, compilation, and assembly generation. The application will independently decode the machine-code instructions so that it can display their encoding fields.

The project will not execute compiled programs. Its purpose is to visualize the compilation process, not to simulate a processor.

The initial implementation will support small, self-contained C programs that can be compiled using the selected toolchain. More advanced C features will be supported only when they work reliably with the chosen compiler configuration.

## 2. Technical Requirements

### 2.1 Functional Requirements

| ID | Requirement | Priority |
|---|---|---|
| FR-1 | Allow users to enter or edit C source code in the browser. | Required |
| FR-2 | Allow users to compile their source code into RISC-V assembly. | Required |
| FR-3 | Display the generated assembly in a separate pane. | Required |
| FR-4 | Display the hexadecimal and binary encoding of each supported instruction. | Required |
| FR-5 | Decode supported RV32I instructions into their encoding fields. | Required |
| FR-6 | Highlight related C, assembly, and machine-code entries when the user selects or hovers over a source line. | Required |
| FR-7 | Display useful compilation errors when the source code cannot be compiled. | Required |
| FR-8 | Allow users to switch between `-O0` and `-O2` optimization levels. | Required |
| FR-9 | Include at least three example C programs with suggested exploration exercises. | Required |
| FR-10 | Provide setup instructions, a test suite, and a technical report. | Required |

### 2.2 Non-Functional Requirements

The application should:

- Be simple enough for students to use without extensive instructions.
- Produce consistent results for the same source code and compiler settings.
- Keep the three panes synchronized without noticeable delays during normal use.
- Report unsupported instructions or missing source mappings rather than displaying incorrect information.
- Handle invalid source code and compiler errors without crashing.
- Be installable by another student or instructor using the project documentation.
- Keep compilation work separate from the web interface so that compiler failures do not interrupt the entire application.

### 2.3 Definition of Success

The project will be considered successful when a user can enter a supported C program, compile it, inspect the resulting assembly and machine code, and select source lines to explore their relationship.

The final version must also pass the project's instruction-decoding tests, include the required educational examples, and provide documentation sufficient for another student to run the application.

## 3. System Architecture

### 3.1 Architecture Overview

The application will use a browser-based frontend and a small backend server.

The frontend will manage source editing, display the compiler output, and coordinate highlighting between the panes. The backend will compile submitted source code and return the assembly and machine-code information.

A separate instruction decoder module will interpret the machine-code words.

The system will have four main components:

| Component | Responsibility |
|---|---|
| Frontend | Source editing, displaying results, and coordinating selection and highlighting. |
| Backend | Accepting requests, running the compiler, collecting output, and returning results. |
| Compiler toolchain | Translating C source code into RISC-V assembly and machine code. |
| Instruction decoder | Extracting the encoding fields from supported RV32I instructions. |

### 3.2 Technology Choices

The project will use the following technologies unless implementation testing reveals a significant compatibility issue.

| Technology | Purpose |
|---|---|
| HTML, CSS, and JavaScript | Build the browser interface. |
| C | Implement the backend and custom instruction decoder. |
| Mongoose | Provide a lightweight HTTP server in C. |
| GCC cross-compiler | Compile C programs for the RISC-V target. |
| GNU Binutils | Inspect compiled files and obtain disassembly information. |
| DWARF debug information | Help associate generated instructions with source-code lines. |
| cJSON | Parse and generate JSON for communication between the frontend and backend. |
| Make | Provide repeatable build and test commands. |

The exact compiler executable names and versions will be recorded in the repository documentation. The implementation must verify that the selected compiler supports the required RISC-V target and options.

A GCC-based toolchain is the planned default. Clang may be considered if GCC cannot meet a demonstrated project requirement, but supporting both toolchains is not part of the initial scope.

## 4. Compilation Pipeline

### 4.1 Overview

When a user selects **Compile**, the following process will occur:

1. The frontend sends the source code and selected optimization level to the backend.
2. The backend validates the request and creates a temporary workspace for the compilation.
3. The compiler translates the C source into a RISC-V executable containing debug information.
4. GNU Binutils obtains the assembly and instruction addresses from the compiled output.
5. The backend reads the compiled instruction bytes and passes supported instructions to the custom decoder.
6. Debug information is used to associate instruction addresses with C source lines.
7. The backend combines the results into a structured response.
8. The frontend updates all three panes and enables linked highlighting.
9. The backend removes the temporary compilation files.

If compilation fails, the backend returns the compiler's useful error messages rather than attempting to display incomplete results as a successful compilation.

### 4.2 Compiler Configuration

The compiler will target RV32I with the ILP32 data model.

The principal options will be:

- `-march=rv32i`: Selects the RV32I instruction set.
- `-mabi=ilp32`: Selects the 32-bit RISC-V calling convention and data model.
- `-g`: Includes debugging information used for source mapping.
- `-O0` or `-O2`: Selects the requested optimization level.
- `-ffreestanding`: Indicates that the program is being compiled in a freestanding environment.
- `-nostdlib`: Avoids automatically linking the standard system libraries.
- `-mno-relax`: Disables linker relaxation so that some instruction transformations are avoided.

The exact command will be tested and adjusted for the selected toolchain. Options will be passed as separate arguments to the compiler, not assembled into a shell command.

The application will initially support small programs that compile successfully under this configuration. The project will not attempt to implement a complete C runtime or standard library.

**Important limitation:** These compiler options do not guarantee that every C program will compile. Programs that depend on library functions or compiler-generated runtime helpers may fail to link. The documentation will describe the tested program subset and explain these limitations.

### 4.3 Compilation Output

The backend will collect:

- Compiler diagnostics.
- Generated assembly.
- Instruction addresses.
- Machine-code bytes.
- Available source-line information.

The compiled file will be the authoritative source for machine-code bytes. The application will not attempt to reconstruct the machine code by converting assembly text into binary.

This distinction is important because assembly output may contain labels, directives, comments, and other lines that are not instructions.

### 4.4 Linking and Instruction Addresses

The backend will use a linker configuration appropriate for the selected bare-metal toolchain.

The configuration must produce a valid output file with a known entry symbol and a layout that the backend can inspect. The project does not require the program to execute.

The implementation will verify that:

- The output is a valid executable for the intended RISC-V target.
- The executable uses the expected instruction architecture.
- Instruction addresses and bytes can be read reliably.
- The disassembly corresponds to the compiled output.
- The backend does not interpret unrelated file data as instructions.

The linker configuration will be kept as simple as possible. A custom linker script will be introduced only if required to produce consistent output for the selected toolchain.

## 5. Machine-Code Decoding

### 5.1 Purpose

The custom decoder will take a 32-bit machine-code word and identify its encoding fields.

It will not compile C or generate machine code. Those responsibilities belong to the compiler.

The decoder exists so the application can independently explain how an instruction is represented in binary.

### 5.2 Supported Instruction Set

The decoder will support the standard 32-bit RISC-V instruction formats used by RV32I:

| Format | Typical instructions | Main fields |
|---|---|---|
| R-type | `add`, `sub`, `and`, `or` | `opcode`, `rd`, `funct3`, `rs1`, `rs2`, `funct7` |
| I-type | `addi`, `lw`, `jalr` | `opcode`, `rd`, `funct3`, `rs1`, immediate |
| S-type | `sw`, `sb` | `opcode`, `funct3`, `rs1`, `rs2`, immediate |
| B-type | `beq`, `bne` | `opcode`, `funct3`, `rs1`, `rs2`, branch immediate |
| U-type | `lui`, `auipc` | `opcode`, `rd`, upper immediate |
| J-type | `jal` | `opcode`, `rd`, jump immediate |

These formats share some fields, but the positions and meanings of those fields vary by format.

The decoder will identify the instruction format before interpreting format-specific fields.

### 5.3 Decoding Process

For each 32-bit instruction, the decoder will:

1. Extract the opcode.
2. Identify the instruction format and operation.
3. Extract the fields relevant to that format.
4. Validate the field combinations required by the instruction.
5. Calculate the interpreted immediate value where applicable.
6. Return the result to the backend.

For example, an R-type instruction contains destination and source register fields, while a branch instruction contains two source registers and a branch offset.

Not every field applies to every instruction. The interface will display only the fields relevant to the selected instruction and will not present nonexistent fields as meaningful values.

The decoder will also distinguish between an immediate's encoded bit pattern and its interpreted value. For example, a branch instruction's encoded immediate bits represent an offset rather than a complete destination address.

### 5.4 Decoder Data Structure

Each decoded instruction will contain information similar to the following:

```c
typedef struct {
    uint32_t address;
    uint32_t machine_word;

    char mnemonic[16];
    char format[8];
    char status[16];

    int rd;
    int rs1;
    int rs2;
    int funct3;
    int funct7;

    int has_rd;
    int has_rs1;
    int has_rs2;
    int has_funct3;
    int has_funct7;

    int32_t immediate;
    int has_immediate;
} DecodedInstruction;
```

This is a proposed starting point, not a requirement to use these exact field names. The final implementation may use enums for instruction formats and decoding status to reduce errors.

The `has_*` fields indicate whether a value is meaningful for the decoded instruction. For example, an instruction that does not use `rs2` must not display a fabricated source register.

The status will indicate whether an instruction was decoded successfully or is unsupported or invalid under the decoder's rules.

### 5.5 Unsupported Instructions

The initial implementation targets RV32I. It will not claim to decode every possible RISC-V extension.

If the compiler emits an instruction outside the supported set, the application will still show its available assembly text and machine-code representation. The encoding pane will identify it as unsupported rather than inventing an interpretation.

The compiler configuration should minimize unsupported instructions, but the application must handle them safely if they appear.

### 5.6 Decoder Testing

The decoder will have unit tests for each supported instruction format and representative instructions.

Tests will verify:

- Correct opcode and register extraction.
- Correct function-field extraction.
- Correct immediate reconstruction and sign extension.
- Correct handling of instructions that use different formats.
- Correct rejection or identification of invalid field combinations.
- Correct handling of unsupported instructions.

Expected results will be checked against trusted RISC-V reference examples and the output of the selected toolchain.

The test suite will also compare decoded instruction fields with the assembly and machine-code output produced by the compiler toolchain.

## 6. Source-Line Mapping

### 6.1 Purpose

Source-line mapping connects the original C code to the assembly instructions generated by the compiler.

This feature is essential because the compiler may translate one C line into multiple instructions, combine the effects of several source lines, or remove source operations entirely during optimization.

The application must therefore use compiler-generated debug information rather than assume that the first C line corresponds to the first assembly instruction.

### 6.2 Mapping Approach

The compiler will generate DWARF debug information through the `-g` option.

The backend will use the available debug line information to associate machine-code addresses with source files and line numbers. The instruction addresses will then be matched to the corresponding assembly and machine-code entries.

For the initial implementation, the project will use a line-oriented mapping approach. It will not attempt to highlight individual C tokens or precisely explain every compiler optimization.

The source line recorded in the mapping will use a clearly documented convention, such as a one-based line number matching the line displayed in the editor.

### 6.3 Mapping Limitations

Source mapping is not always one-to-one.

Examples include:

- One C line generating several assembly instructions.
- Several C statements contributing to the same instruction.
- An optimized statement generating no separate instruction.
- An instruction having no useful source-line mapping.
- Multiple instructions being associated with the same source line.

The application will support these situations without claiming that every instruction has exactly one corresponding C line.

When a mapping exists, selecting a source line will highlight the associated instructions. When no mapping exists, the application will leave unrelated entries unhighlighted and may display a brief message explaining that a direct mapping is unavailable.

The application will not invent source-line relationships merely to keep the panes synchronized.

### 6.4 Mapping Tests

The mapping system will be tested with programs containing:

- Simple arithmetic.
- Conditional statements.
- Loops.
- Function calls.
- Array access.
- Code compiled at `-O0` and `-O2`.

The tests will confirm that the application uses actual debug information and that missing or multiple mappings do not cause incorrect highlighting.

The project will prioritize reliable line-level mapping over more advanced explanations of how optimization changes individual statements.

## 7. Frontend Design

### 7.1 Three-Pane Layout

The browser interface will contain three visible panels.

**Pane 1: C Source**

- Displays the user's C program.
- Allows the user to edit the source.
- Shows line numbers.
- Supports clicking and hovering over source lines.
- Provides a compile button and optimization-level selector.

**Pane 2: RISC-V Assembly**

- Displays the assembly generated by the compiler.
- Shows instruction addresses and assembly text.
- Highlights instructions associated with the selected source line.
- Allows users to select instructions and view their corresponding encoding.

**Pane 3: Machine Code**

- Displays each supported instruction's hexadecimal and 32-bit binary representation.
- Shows a color-coded breakdown of the relevant encoding fields.
- Highlights machine-code entries associated with the selected source line.
- Indicates when an instruction is unsupported or lacks a source mapping.

The layout should adapt to smaller screens where practical, but the primary target is a desktop browser where all three panes can be viewed together.

### 7.2 Highlighting Behavior

The application will maintain one shared selection state that identifies the currently selected source line or instruction.

When a user hovers over a source line, the application will temporarily highlight related entries in the other panes. When the user clicks a source line, the selection will persist until another line is selected or the selection is cleared.

Selecting an assembly instruction will also highlight its machine-code entry. If source information is available, the corresponding C line will be highlighted as well.

Hover highlighting must not accidentally erase a persistent click selection when the pointer moves between elements.

The implementation will use the mapping information returned by the backend rather than trying to infer relationships from displayed text.

### 7.3 Encoding Visualization

Each decoded instruction will display the relevant encoding fields using consistent colors.

For example, an R-type instruction may show:

- Opcode.
- Destination register (`rd`).
- First source register (`rs1`).
- Second source register (`rs2`).
- Function fields (`funct3` and `funct7`).

Other formats will display their own fields, including immediate values where appropriate.

The same field will use the same color throughout the application. A small legend will explain the colors.

The hexadecimal and binary representations will remain visible so students can compare the complete instruction with its individual fields.

### 7.4 Error Handling

If compilation fails, the application will display the error messages and preserve the user's source code.

The frontend will distinguish between:

- Compilation errors.
- Backend or request errors.
- Unsupported instructions.
- Missing source mappings.

These conditions should not be represented as though they were all compiler errors.

The application will avoid inserting compiler output directly into HTML as executable markup. Text from source code and compiler diagnostics will be displayed as text, not interpreted as HTML.

## 8. Backend and API Design

### 8.1 Backend Responsibilities

The backend will:

- Accept source code and compiler settings.
- Validate request fields and enforce a source-size limit.
- Create an isolated temporary directory for each compilation.
- Invoke the compiler and related tools using controlled arguments.
- Capture compiler diagnostics and generated output.
- Read the compiled machine-code bytes.
- Decode supported instructions.
- Collect source-line mappings.
- Return a structured JSON response.
- Remove temporary files after processing.

The backend will not run the compiled program.

### 8.2 Compile Endpoint

The frontend will send compilation requests to:

`POST /api/compile`

An example request is:

```json
{
  "source": "int main(void) {\n    int x = 2 + 3;\n    return x;\n}\n",
  "optimization": "O0"
}
```

The optimization field will accept only the supported values, initially `O0` and `O2`.

The backend will reject malformed requests, unsupported settings, and source files that exceed the configured size limit.

### 8.3 Response Structure

A successful response will include the generated assembly, decoded instruction entries, and source-line mapping information.

For example:

```json
{
  "success": true,
  "assembly": [
    {
      "address": 65536,
      "text": "addi a0, zero, 5",
      "source_line": 2
    }
  ],
  "instructions": [
    {
      "address": 65536,
      "hex": "0x00500513",
      "binary": "00000000010100000000010100010011",
      "mnemonic": "addi",
      "format": "I",
      "source_line": 2,
      "fields": {
        "opcode": "0010011",
        "rd": "01010",
        "funct3": "000",
        "rs1": "00000",
        "immediate": "000000000101"
      },
      "decode_status": "supported"
    }
  ],
  "diagnostics": []
}
```

The example illustrates the response structure; exact addresses and assembly output will depend on the compiler and linking configuration.

A failed compilation will return `success: false` and include useful diagnostic messages. It will not return stale assembly from a previous compilation as though it belonged to the current source.

The API will use a consistent convention for line numbers, instruction addresses, and missing mappings. A missing source line will be represented explicitly as `null`, not as line zero.

### 8.4 Error Responses

The API will distinguish between invalid requests, compilation failures, and internal errors.

The HTTP status and response body will be consistent for each category. The frontend will use this information to display an appropriate message.

The response will not expose private server paths, environment variables, or unnecessary details about the server's configuration.

## 9. Security and Resource Management

Although the application is intended for educational use, a public version may receive unexpected or malicious source code. The backend must not assume that submitted programs are harmless.

The following measures will be implemented:

1. **No shell command construction:** Compiler programs will be invoked directly with separate arguments rather than by inserting user input into a shell command.
2. **Controlled compiler settings:** Users may select only supported optimization levels. They may not provide arbitrary compiler flags or executable paths.
3. **Temporary workspaces:** Each compilation will use its own temporary directory, which will be removed when processing finishes.
4. **Input limits:** The backend and HTTP server will enforce a maximum request size.
5. **Execution time limits:** Compiler processes will have a defined time limit and will be terminated if they exceed it.
6. **Output limits:** Compiler output and generated files will be limited to prevent excessive resource use.
7. **Concurrency limits:** The backend will limit the number of compilations running simultaneously.
8. **Restricted permissions:** The compiler will run with the minimum permissions practical for the deployment.
9. **Controlled environment:** Unnecessary environment variables, filesystem access, and network access will be restricted where practical.

A process time limit alone is not a complete security boundary. Likewise, limiting one file's size does not limit the total space consumed by all temporary files. The implementation will account for these differences when choosing its controls.

For a publicly accessible deployment, compilation should run inside an appropriately restricted environment, such as a container or other operating-system isolation mechanism, with no unnecessary host mounts, secrets, or elevated privileges.

The project will not attempt to build a sophisticated general-purpose sandbox. It will use existing operating-system and deployment controls appropriate to the hosting environment.

Temporary files must be cleaned up after success, failure, timeout, and cancellation. The application must also avoid leaving compiler processes running after a request has ended.

## 10. Testing and Evaluation

Testing will be performed throughout development rather than postponed until the final week.

### 10.1 Unit Tests

Unit tests will cover the custom instruction decoder.

They will check the field extraction, instruction formats, immediate values, and handling of unsupported instructions.

Each supported RV32I instruction category will have representative test cases.

### 10.2 Integration Tests

Integration tests will compile small C programs and verify that the backend returns consistent assembly, machine-code, and mapping information.

The tests will include:

- A simple arithmetic program.
- A program containing a conditional.
- A loop.
- A function call.
- An array-access example.
- Programs compiled with both `-O0` and `-O2`.
- Invalid C source that should produce a compilation error.
- A case where an instruction has no useful source mapping.

Tests will compare the decoder's output with trusted reference values and verify that the assembly and machine-code entries correspond to the same instruction addresses.

### 10.3 Frontend Tests

Frontend testing will confirm that:

- All three panes update after compilation.
- Selecting a C line highlights the correct mapped entries.
- Selecting an assembly instruction highlights its encoding.
- Missing mappings do not produce incorrect highlights.
- Clicking a line preserves the selection.
- Hovering over another line updates the temporary highlight correctly.
- Compiler errors are displayed without removing the user's source.

### 10.4 Performance and Reliability

The project will test the application with small programs representative of its intended educational use.

It will record compilation time and test behavior under several simultaneous requests. The goal is to provide a responsive classroom tool, not a high-capacity public compilation service.

### 10.5 Evaluation Criteria

The final evaluation will follow the honors project rubric:

| Criterion | Weight | Evidence |
|---|---:|---|
| Compiles valid C to RISC-V | 40% | Successful compilation tests using the documented supported subset. |
| Displays correct RV32I assembly and encodings | 20% | Decoder unit tests and comparisons with reference output. |
| Technical report | 20% | Explanation of architecture, design decisions, limitations, testing, and lessons learned. |
| Linked line-level highlighting | 10% | Demonstration and tests covering mapped and unmapped source lines. |
| Example programs and exercises | 10% | Three to five examples covering different compiler behaviors. |

The application will not claim support for all possible C programs. Its supported compiler configuration and limitations will be documented, and the tests will focus on clearly defined examples.

## 11. Example Programs and Educational Use

The final project will include three to five small C programs with suggested exercises.

The examples should be selected to demonstrate different relationships between C and generated instructions.

### Example 1: Arithmetic

A program that performs simple integer calculations.

**Exploration exercise:** Identify the instructions that implement arithmetic operations and examine the encoding fields of an immediate instruction.

### Example 2: Conditional Statements

A program containing an `if`/`else` statement.

**Exploration exercise:** Find the branch instruction and examine its source registers and branch offset.

### Example 3: Loops

A program containing a `for` or `while` loop.

**Exploration exercise:** Identify the instructions used to implement the loop condition and the jump back to the loop body.

### Example 4: Function Calls

A program containing a simple function and a call to that function.

**Exploration exercise:** Compare the assembly generated for the function call and return at different optimization levels.

### Example 5: Optimization

A program suitable for comparing `-O0` and `-O2`.

**Exploration exercise:** Compare the two outputs and identify changes such as removed instructions, different register use, or simplified calculations where they occur.

The examples will be small enough for students to understand without needing advanced knowledge of C or compiler internals. Their accompanying exercises will ask students to observe and explain the generated output rather than assume that every source operation corresponds to a unique instruction.

## 13. Risks and Limitations

### 13.1 Compiler Configuration

**Risk:** The chosen compiler may require runtime support or additional configuration for some programs.

**Response:** Test the compiler configuration early, use small self-contained examples, and document the supported subset of C.

### 13.2 Source-Line Mapping

**Risk:** Optimization can remove, combine, or rearrange instructions, making source relationships less direct.

**Response:** Use compiler-generated debug information and support multiple or missing mappings. Do not assume one C line always produces one instruction.

### 13.3 Decoder Errors

**Risk:** An incorrect field extraction or immediate calculation could mislead students.

**Response:** Implement the decoder as a separate module with unit tests and compare its results with trusted reference values.

### 13.4 Public Deployment

**Risk:** Submitted source code can consume excessive resources or exploit weaknesses in the compiler environment.

**Response:** Restrict inputs, compiler options, execution time, output size, permissions, and concurrency. Use operating-system isolation appropriate to the deployment.

### 13.5 Optimization Differences

**Risk:** The assembly produced by different compiler versions or settings may differ, making exact output comparisons unreliable.

**Response:** Document the toolchain version and compiler flags. Tests should verify instruction correctness and behavior rather than depend unnecessarily on one exact assembly listing.

## Conclusion

The C-to-RISC-V Three-Pane Visualizer will provide students with an interactive way to explore the relationship between C code, assembly instructions, and machine-code encodings.

By using an existing compiler, implementing a focused RV32I decoder, and relying on compiler-generated debug information for source mapping, the project concentrates its development effort on the features most relevant to the educational goal.

The scope is intentionally limited to a single target architecture, a small backend, and line-level highlighting. This makes the project achievable within the semester while still requiring meaningful work in systems programming, compiler toolchains, instruction encoding, web development, testing, and educational software design.
